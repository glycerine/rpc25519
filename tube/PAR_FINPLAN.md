# PAR completion plan

## 1. Detailed current status

Audit baseline: 2026-10-17, before implementation. The findings and baseline verification in this section record that original review; they are not descriptions of the subsequently implemented behavior. Current implementation, verification, and remaining requirements are recorded in the implementation checkpoint in section 3. Implementation was subsequently authorized by the user. Existing unrelated working-tree changes, including client-session recovery, are outside this plan.

### Scope and correctness target

Tube has useful local detection machinery, but not a working PAR recovery protocol. The immediate objective should be recoverable WAL corruption, with an explicit boundary around snapshots, YogaDB state, and node-local persistent metadata. Calling the entire feature complete requires those boundaries to be addressed too.

The reference is [Protocol-Aware Recovery for Consensus-Based Storage, FAST 2018, §§3–4](https://www.usenix.org/system/files/conference/fast18/fast18-alagappan.pdf). Its essential rules are: preserve committed data; distinguish interrupted writes from storage damage; identify damaged entries independently; allow election with identifiable damaged entries, but repair the leader before normal service; distinguish valid data, known damage, and proven absence; discard a damaged leader suffix only after a majority of the other replicas establish absence. Missing replies and damaged copies are not absence. Snapshot recovery and node-local metadata require separate treatment. The [authors' crash/corruption proof](https://research.cs.wisc.edu/adsl/Software/par/proof.pdf) explains why an unordered final write can remain ambiguous. These rules guide the Tube-specific proposal below; the existing informal notes are not a substitute for them.

Assumptions to document and enforce: crash/restart failures plus detectable storage faults, non-Byzantine peers, reliable checksum detection, and storage honoring successful sync operations. A checksum cannot establish integrity against a coordinated alteration of both data and its independently stored evidence. Unrecoverable evidence must leave the affected node or operation unavailable, without silently manufacturing an empty log.

### Audit findings, in priority order

**F1 — Recovery cannot currently run after detection.** `newParLog` panics on partial file size, malformed records, and checksum faults. `loadRaftLogEntry` decodes before validating the hash and panics on damaged framing, checksum objects, hashes, and identifiers. `initWalOnce` also panics on error. There is no inventory of holes, recovery state, request handler, repair installation, or service gate. This is a completion blocker, not a small missing retry.

**F2 — Crash classification cannot assume uniform data-before-identifier ordering.** In a normal single append, the main file is synced before `append1`. In follower `overwriteEntries`, individual entries use `doFsync=false`, but each `append1` syncs the sidecar; the WAL sync happens at the end. Compaction also writes with `doFsync=false`. Leader `replicateBatch` syncs the main file only for its last entry, while previous identifiers have already been synced. A crash can therefore leave valid identifiers pointing to incomplete data for more than just the final entry of a batch. A sync of one file does not order writes to the other. The sidecar also adds one sync per record despite batching comments. Do not port a last-entry-only classification rule without first fixing or explicitly modeling these write sequences.

**F3 — Length semantics are inconsistent with the comments.** `wal.go:489` passes `nw0` as the framed entry size and `nw2` as the checksum-frame size. `par.go:105–106` describes the second length as the entry size including checksum. Today neither length drives recovery, so the discrepancy is latent; a recovery scanner using the comment would calculate the wrong boundary. Preserve the existing on-disk meaning for compatibility: total span is `Len0 + Len2`. Validate both before using them.

**F4 — Structural sidecar corruption can escape cross-checking.** In `validateParLog`, offset, ticket ID, index, term, and cluster comparisons are inside `if h != pr.RLEblake3`. If the entry hash matches, inconsistent metadata is accepted. Lengths and `Epoch` are not checked. `loadPathHelper` does not reconcile total WAL records with sidecar records. A complete missing WAL suffix can look like clean EOF even when identifiers survive. An empty WAL returns before comparing a nonempty sidecar. Conversely, opening a missing sidecar creates an empty file, then the existing WAL fails lookup. These cases require explicit classification, not automatic truncation, identifier fabrication, or fresh-node bootstrap.

**F5 — Framing is not bounded by trusted recovery boundaries.** `loadone` calls general `nextframe`, whose size comes from untrusted bytes and can cross a 400-byte slot. `msgbin.go:11–40` can allocate according to a damaged bin32 length before a checksum is checked. Its helpers also panic on several malformed/short-read cases. A PAR scanner must use bounded reads and independently verified offsets; otherwise one damaged frame prevents inspection of healthy later entries. Do not catch arbitrary panics and resume scanning by guessing byte positions.

**F6 — Error paths and in-memory state need repair.** `append1` modifies `s.e` before its disk write succeeds; `truncate` changes count/slice before checking persistence and ignores `Truncate` errors. Negative `at` and negative truncation counts can panic through indexing/slicing; integer multiplication and range bounds are unchecked. Multiple I/O functions advertise errors but panic or ignore subordinate errors. Constructor failure can leak descriptors. The 400-byte slots are not guaranteed atomic disk writes: successive slots can straddle sector boundaries. CRC detection is useful, but cannot justify an atomicity assumption.

**F7 — Two-file replacement has no crash-consistent selection rule.** Production compaction renames the new sidecar before the new WAL (`wal.go:1307–1316`), then syncs the directory. A crash between renames can expose a mismatched pair. `installedSnapshot` truncates the WAL before truncating the sidecar. Suffix overwrite truncates identifier evidence before writing the replacement WAL. Interrupted overwrite, compaction, and snapshot installation must be distinguishable from post-durability corruption. Rewriting a pair during repair would inherit the same problem unless selection is made atomic.

**F8 — Existing summaries are not PAR evidence.** RequestVote/Vote and AppendEntries/Ack contain term/index and membership data, but no checked payload evidence or damaged/absent distinction. `TermsRLE` describes terms, not content integrity. `RaftLogEntry.CurrentCommitIndex` records older commitment knowledge, not a proof that the containing entry is uncommitted. Cached peer descriptions, a short log, a timeout, or a compacted-away entry cannot be counted as a negative acknowledgment. A recovery decision must be bound to its election term, exact entry identity, membership configuration, and query round.

**F9 — Pre-vote notes are unfinished and overstate what a gate proves.** The prose at `tube.go:14934` and `tube.go:18255` includes externally generated design discussion, not implemented guarantees. Actual pre-vote handlers use ordinary freshness checks. Rejecting every damaged candidate would defeat the all-nodes-partially-damaged availability cases. Matching whole-log hashes would also reject legitimate divergent suffixes. Performing a check during pre-vote cannot protect against corruption discovered after election or prove that Tube's logless membership transitions are safe under this fault model. Treat membership/recovery interaction as a separate proof and test obligation.

**F10 — WAL repair alone cannot repair all persisted state.** Saved state contains safety-critical term/vote and membership information. Blindly copying a peer's state cannot restore a node's own voting history safely. `applyNewStateSnapshot` currently saves new state before clearing the old WAL and notes the unfinished atomic handoff (`tube.go:17583` onward). Snapshot transport checksums are useful, but do not establish a durable repairable snapshot generation, nor integrity of every YogaDB page. Keep these limitations visible in the rollout contract.

## 2. Unit-testing scenarios covering the needed PAR behavior

Put the new hand-written tests in `par_test.go`. Use a small table-driven decision model plus real temporary-file fixtures; do not build a second consensus implementation in the tests. Each `t.Run` must be outside its own `bubbleOrNot`/synctest bubble. Give every case independent state in a uniquely named local test directory under `tube/`, rather than using `t.TempDir`. Remove the directory only when the test passes; retain it on failure and log its absolute path so the WAL, sidecar, and crash images can be inspected. Use simulated time/network events instead of wall-clock sleeps. For disk ordering, model durable file images explicitly: closing a normal file flushes writes and is not a power-failure simulation.

Each test should identify its oracle: acknowledged commands survive; state-machine application stays ordered and exactly once; committed index and retained snapshot barrier do not move backward; healthy suffix entries survive repair; recovery decisions use only current, distinct, eligible members; unsafe/unknown evidence produces a bounded wait/error without modifying durable evidence. Test both the decision and the reopened on-disk result.

### A. Local format, identity, and inventory

1. Round-trip empty/one/many sidecar slots and WAL entries; reopen after append/truncate/append. Cover ordinary and compacted bases, including an empty WAL anchored by a snapshot. Assert exact offsets, both existing length meanings, hashes, index/term, cluster and ticket IDs, and next append position.
2. Keep the sizing test, adding actual maximum supported string lengths and a clean oversized-record error. Test negative counts/indices, zero/overflowing lengths, overflowing offsets, overlaps, gaps, duplicate indices, impossible predecessor links, and term/index identity conflicts.
3. Flip bytes independently in the frame prefix, payload, checksum frame, CRC, and each metadata field. Recompute only the sidecar CRC when testing semantic checks, so a valid CRC cannot hide bad metadata. Define whether unused padding is ignored; do not accidentally promise it is checksummed.
4. Corrupt the first, middle, and final entry; corrupt adjacent and separated entries. A valid identifier must allow subsequent healthy entries to be inventoried without decoding damaged payload. Verify that a neighbor's chain-check failure does not destroy an independently valid neighbor.
5. Cover missing WAL, missing sidecar, unexpected empty files, extra complete slots, partial final slots, missing complete WAL suffix, and extra/trailing bytes. Test a new directory separately from a damaged existing installation. Neither absent files nor clean EOF alone prove an uncommitted suffix.
6. Test read, seek, write, sync, truncate, close, rename, and directory-sync errors; short writes; read-only files; malformed/truncated frames; and invalid claimed allocation sizes. Errors must retain the last durable state and close resources. Keep any I/O seam package-private and limited to PAR operations.
7. If one of entry/identifier is bad, test reconstruction using the independently checked other source plus authorized peer evidence. If both are unusable, require explicit unavailability. Startup/recovery checks must validate persisted state rather than trusting cached objects.

### B. Crash and corruption classification

Enumerate crash cut points for single append, leader batch, follower batch, suffix overwrite, compaction, and snapshot handoff: before data, during data, after WAL sync, during identifier write, after identifier sync, during generation publication, and after publication before cleanup. Include every persisted/not-persisted combination actually allowed by the two-file ordering. Test the supported storage format; missing required metadata must not trigger initialization from an older format.

Expected outcomes must distinguish intact, provably interrupted/unacknowledged suffix, identified corruption, ambiguous damage, and unusable evidence. An ambiguous tail remains protected until resolved. A partial identifier is not automatically proof of an interrupted data write. Losing a whole acknowledged suffix, having fewer sidecar records, and observing a damaged last record must never silently shorten durable history. Inject post-sync bit flips separately from crashes to ensure the classifier does not conflate them.

### C. Distributed recovery decisions

Use explicit response states: valid matching bytes, matching identifier but damaged bytes, proven absence, compacted/needs snapshot, and unavailable/unknown. Cover N=1, N=3, N=4, and N=5, and all distinct arrival permutations for the small decision tables.

| Scenario | Required assertion |
| --- | --- |
| Healthy current leader supplies the exact damaged follower entry | Repair durably; next read/restart returns the acknowledged value. |
| Same index but another term, ticket, cluster, or conflicting digest | Never install as the requested entry; classify legitimate obsolete suffix separately from inconsistent evidence. |
| Recovering leader has one damaged entry and one valid donor | Validate and install the donor copy; require no majority of identical payload copies. |
| Five-node recovering leader sees two proven absences and two silent peers | Wait; do not add the damaged leader's self-vote to the negative evidence. |
| Three distinct eligible followers prove absence in that five-node round | Only an otherwise authorized, unfenced suffix may be discarded; preserve the good prefix. |
| Two absences plus one damaged copy | Remain unresolved. Damaged is not absent. |
| All copies of a protected entry are damaged | Remain unavailable, preserving identifiers and acknowledged history. |
| One intact copy is temporarily unreachable | Wait, then repair when it returns; a timeout must not authorize truncation. |
| Known committed/applied entry plus contradictory absence responses | Fail closed and expose an invariant violation; never override the durable commitment floor. |
| Duplicate, reordered, delayed, wrong-round, wrong-incarnation, nonmember, or wrong-cluster replies | No extra votes and no stale repair. |
| Higher term, leadership loss, membership version change, or local WAL mutation mid-round | Invalidate evidence and restart/reject the round before installation. |
| Remote entry compacted behind a snapshot | Return snapshot/unknown evidence, never an absence vote. |
| Repair bytes fail hash/framing/identity checks or local persistence fails | Keep the hole and service gate; do not acknowledge successful repair. |

The fixed-membership negative threshold is `floor(N/2)+1` distinct **other** voting members, not a majority of whichever responses arrived. For N=1 a damaged local entry cannot be declared disposable just because there are no peers. Test quorum arithmetic at even sizes as well as the usual odd sizes. Changing membership requires the configuration-specific extension in section 3, not this arithmetic applied blindly.

### D. Activate the six existing scenarios

Use `genParTestScenarios` as input, with explicit entries 1–3 and acknowledged results. For each row choose every eligible node as the recovering leader, including nodes with holes. Check all repaired entries and then restart/replay. Translate `lagging` into an explicit prefix, rather than leaving the flag as an unimplemented fixture detail.

| Existing scenario | Fault layout, using zero-based node/entry arrays | Required outcome |
| --- | --- | --- |
| 0 | Node 0 entry 0 damaged; nodes 3 and 4 down | Remaining nodes recover and serve. |
| 1 | Node 0 entry 0 damaged; nodes 3 and 4 lagging | Lagging nodes cannot cause committed history to be discarded. |
| 2 | Node 0 entry 0 and node 1 entry 1 damaged; node 4 down | Recover both entries from available complementary copies. |
| 3 | Same two damaged entries; node 4 lagging | Recovery must not rely on the lagging node as a donor for absent entries. |
| 4 | Nodes 0, 1, 2 have distinct damaged entries | Recover although no clean majority exists. |
| 5 | Every node has a damaged entry, with complementary intact copies | Elect/recover without requiring a completely healthy leader or healthy majority. |

Also test a three-node version with one distinct damaged entry per node. Add the destructive counterexample: a damaged up-to-date replica plus lagging replicas must not become an apparently empty leader that overwrites the only remaining committed history when other nodes return.

### E. Lifecycle, elections, application, and persistence boundaries

* Start with disk damage before opening the node; recovery transport must become reachable without normal service. Test corruption discovered while already leader and while follower, plus recurring corruption after a successful repair.
* Retain logical last index/term from trustworthy identifiers during elections; a hole must not make a log appear shorter. Reject grants when required metadata is unknown. A recovering leader must not append its normal initial no-op, serve local read leases, apply commands past a hole, change membership, or send an authoritative replacement snapshot before its recovery barrier clears. Term/vote persistence and duplicate-vote protection remain intact.
* Repair multiple holes in order, with an already-applied prefix, pending sessions, CAS/write operations, and membership commands. Avoid replaying commands already represented in durable application state. Preserve session results and `LastApplied` across restart.
* Crash during repair and immediately after repair acknowledgment. Reopen the selected generation, validate every record and predecessor, rebuild terms, and append a new command. Repeat the recovery to establish idempotence.
* Crash between each old/new WAL-sidecar rename and snapshot/state/WAL handoff. Reject mixed generations. Preserve valid snapshot barriers and membership provenance when prefixes are compacted.
* Freeze membership for initial supported recovery rounds. Then test term/configuration changes, removed nodes, shadow replicas, and logless reconfiguration. A removed or shadow node may supply checked bytes where appropriate, but must not count toward a voting absence certificate. Never mix certificates from different configurations.
* Test saved term/vote metadata loss independently from replicated-log loss. Do not restore a missing vote record from a peer. Validate snapshot identity, boundary index/term, checksum, size, membership and session/application state. Treat YogaDB recovery as its own obligation; memory snapshots do not establish page-level recovery.
* Retain healthy-path regression and performance checks: no additional network round on ordinary commands, bounded recovery messages/memory, one WAL sync and one sidecar sync per chosen batch rather than per entry, and no extra goroutine/service framework solely for PAR. Run targeted tests normally, with `-tags synctest`, and with `-race`; then existing election, membership, snapshot, restart, WAL, persistor, and client tests.

## 3. Implementation plan

### File budget and staged deliverables

Keep classification, inventory, recovery decisions, message handling helpers, and repair routines in `par.go`; keep all new hand-written tests in `par_test.go`. Package methods on `TubeNode` and `raftWriteAheadLog` can live in `par.go`, so do not create a separate recovery package, worker service, or generic storage framework.

**Two files are sufficient for a tested local/recovery decision core, but not for enabling production PAR.** Existing execution paths never call that core, and existing readers panic before recovery can run. The smallest credible integrated WAL change also needs short hooks in `wal.go` and `tube.go`. Full persisted-state protection additionally needs `persistor.go` and potentially the YogaDB boundary. Do not hide these dependencies or call a two-file prototype complete.

| File | Proposed change boundary |
| --- | --- |
| `par.go` | All new hand-written PAR logic; bounded reader; evidence types; recovery state machine; exact-span repair and any necessary publication helpers. |
| `par_test.go` | Unit decision tables, disk images/crash cuts, scenario and integration tests. |
| `wal.go` | Delegate load/validation and coordinated flush/install operations to PAR; preserve existing normal APIs where possible. |
| `tube.go` | Minimal per-node recovery state, startup/event dispatch hooks, and service/election/replication gates. Keep handler bodies in `par.go`. |
| `persistor.go` | Only when implementing the explicit metadata/snapshot durability milestone; local safety metadata cannot be repaired with WAL code alone. |
| Generated files | Regenerate only if serialized structures change. Prefer small explicit versioned recovery messages owned by `par.go`; do not hand-edit generated code or add fields across all existing Raft messages. |

Use a PAR-specific bounded reader instead of broad changes to `msgbin.go`, unless the implementation demonstrates an unavoidable common-reader dependency. Do not alter client helpers, Hermes, unrelated reconfiguration algorithms, or existing tests just to make recovery tests pass.

### Step 1 — Specify evidence and build the local inventory

Define a small package-private status enum and contextual error/report type: intact, interrupted suffix, damaged but identified, and unknown/unusable. Use static errors for fixed failure classes; carry entry/location details in a structured result rather than allocating formatted strings on every lookup. Keep programming-invariant panics distinct from expected disk-fault results.

Use `(ClusterID, Term, Index)` as the log identity, cross-checked with ticket ID and the stored digest. Tube's membership `CurrentEpoch` is not a replacement for the Raft entry term. Keep existing `ParRecord` wire fields and its unused zero `Epoch`; document the unused field rather than changing its meaning speculatively.

Read slots with `ReadAt`/bounded buffers; check CRC, framing, ranges, and identity before consuming offsets. Read WAL data using verified spans and file-size bounds. Keep a sparse inventory that includes identified holes and healthy later entries. Rebuild logical terms from validated entry/identifier evidence, never from zero placeholders masquerading as commands. Return a report for reconciliation with restored commit/applied/snapshot state before discarding anything. Do not silently create missing history during opening.

Acceptance: section 2A and the read-only classification parts of 2B pass. Healthy existing WALs/sidecars retain their format and load correctly. No distributed behavior is enabled yet.

### Step 2 — Make durability and file selection explicit

Choose strict batch ordering for new writes: stage identifiers while writing a WAL batch; sync the WAL; publish/write the batch's identifiers; sync the sidecar; only then acknowledge the batch. Route single append, follower append, leader batch, close, and compaction construction through that ordering. Move in-memory durable counts only after successful persistence. Preserve batching; do not fix ordering by adding a WAL sync per record.

No upgrade paths or migration safeguards are supported. Existing saved state requires the current storage layout, including at least one valid local term/vote metadata copy. Only an empty state store may initialize a new pair. Ambiguous acknowledged boundaries remain protected until recovery resolves them.

Prefer exact-span, idempotent repair using the original validated identifier and matching serialized bytes. If the repair preserves every record boundary and identity, retain the sidecar evidence, rewrite only the damaged WAL span/integrity data, sync, and revalidate before clearing the hole. A crash during this repair should leave the same identified hole recoverable again. Prove this with crash cuts before introducing a new generation format; simple entry repair should not require rewriting an entire log or adding a manifest.

For destructive suffix replacement, compaction, and snapshot handoff, specify a crash-consistent selection rule before reuse. If validated original/replacement files cannot provide an unambiguous rule with a smaller change, use a small shared generation protocol: sync replacement files, validate the pair, atomically publish a checked selector, sync its directory, and retain the previous usable generation until publication is durable. Selector damage must be handled explicitly; it is new safety-critical metadata. This is a design choice to resolve during review, not a requirement to build a general manifest system.

This is the main unavoidable scope expansion beyond two files. If generation publication is deferred, support only operations for which crash safety is established and report the unsupported recovery cases explicitly; do not enable destructive repair atop the current two-rename sequence.

Acceptance: every disk mutation in section 2B has a crash-cut oracle; newly acknowledged entries survive restart; partial replacements select a complete validated generation or stop safely.

### Step 3 — Implement the decision core before transport

Implement a deterministic, package-private recovery-round object in `par.go`. Bind it to current leader identity, term, membership version/set, exact damaged identity, and a request ID. Keep distinct per-member results. Its only outputs are validated repair candidate, authorized suffix-discard proposal, wait, or invariant/error. Timeouts only release resources or schedule retry; they never strengthen evidence.

Make absence a positive assertion produced by a validated inventory under the round's configuration, not an inference from a failed lookup. Exclude compacted ranges, unknown metadata, damaged identifiers, and in-progress destructive transitions. Preserve known commitment/application floors. Resolve conflicting valid identities as an explicit inconsistency; do not pick whichever arrives first.

Start with stable membership and forbid initiating membership changes from an unresolved recovering leader. Recovering followers must still durably adopt newer configurations received from the leader; otherwise an older configuration can prevent admission of the very snapshot needed for recovery. Adoption invalidates the previous recovery fence and does not acknowledge damaged log data. After that core is proven, adapt certificates to Tube's actual logless membership rules and transition safety; restarting a round on a version change is necessary but is not itself a proof across historical configurations. Until that extension is verified, keep the stable-membership support restriction explicit.

Acceptance: section 2C and all six scenario decision fixtures pass, including unavailable outcomes and every response ordering. A clean-majority or clean-candidate prerequisite is not introduced.

### Step 4 — Integrate recovery with the existing event loop

Let startup inventory return holes without admitting normal client work. Restore and validate node-local metadata and snapshot anchors; establish connections using trusted membership information. Keep mutation on Tube's existing owner goroutine. Use a small versioned PAR request/reply message family and existing circuit dispatch, with request IDs, cluster/incarnation/term/config checks, bounded payloads, and cancellation on leadership or membership changes. Existing AE term summaries can guide requests, but cannot supply the missing evidence semantics.

Allow elections to use trustworthy logical identities while preserving normal Raft freshness and vote-persistence rules. A leader with holes enters recovery before the normal `becomeLeader` no-op/replication path. Gate local reads, apply/commit progression, client writes, membership changes, and authoritative snapshot/replication output until the relevant history is established. Followers expose useful intact evidence while withholding acknowledgments that would claim damaged data is durable. Keep ordinary verified heartbeats and term handling available so recovery does not trigger avoidable election churn.

A donor must supply checked bytes and the matching identity; verify again at the receiver. Do not reconstruct a corrupt entry by reserializing an arbitrary in-memory object: the hash covers serialized bytes, including predecessor fields, and repair must preserve that representation or deliberately rebuild all affected integrity records under validated generation rules.

Acceptance: section 2D runs against actual nodes, not just a mock decision table; startup with damaged WAL reaches recovery transport; ordinary client results resume only after safe durable repair.

### Step 5 — Install repair and close the persistent-state boundary

Apply only a decision still valid for the current term/configuration/log generation. Validate repaired bytes, retained prefix/suffix, hashes, and predecessor links before clearing the recovery barrier. Prefer the exact-span repair above; rebuild `raftLog`, terms, positions, and sidecar count from checked data after repair or generation publication. Repair identified entries without discarding healthy later history; a separately authorized suffix discard must not cross protected commit/applied/snapshot barriers. Replay only unapplied commands and preserve session deduplication state.

Complete or explicitly defer snapshot and local metadata recovery as separate milestones. For snapshots, establish a verified durable identity/boundary and atomic state/WAL/sidecar handoff before using snapshot transfer as an escape from damaged compacted history. For term/vote metadata, specify redundant local persistence and reconciliation that cannot forget an acknowledged vote. Review how YogaDB durability and `LastApplied` remain atomic enough for exactly-once replay. If those files are damaged and no safe local recovery exists, keep the node fenced; do not fetch another node's voting history.

Recovery support needs an explicit validation path: check persisted state before serving bytes as a repair donor, and run application integrity validation during startup/recovery. PAR does not continuously detect disk damage that occurs after a healthy replica starts; that is outside the requested behavior. On damage detected during recovery, invalidate affected evidence and service readiness while retaining healthy data useful to other recovering nodes.

Acceptance: section 2E, repeated recovery/restart, crash during installation, and corruption-after-election cases pass. WAL-only recovery may ship as a precisely bounded milestone; full PAR is not declared complete while snapshot/metainfo/application-state protection remains deferred.

### Step 6 — Review and rollout criteria

Review the following before enabling PAR for production: the documented storage-fault assumptions; supported-format crash classification; durable batch ordering; protected history floors; membership-specific certificate validity; recovery-only election/service gates; crash-consistent file selection; and the separation of replicated data from node-local term/vote state. Require tests demonstrating both safe waiting and useful recovery, especially the all-nodes-partially-damaged case.

Run the targeted PAR suite with normal time, synctest, and race detection, then the existing relevant regressions. Measure healthy-path allocations and batch sync counts; static error classes should allocate nothing on normal lookup. Keep the final change concentrated in `par.go` and `par_test.go`, with small, reviewable hooks in the existing persistence/event-loop files. The original plan required review before implementation; that review was followed by the user's explicit authorization to implement it.

### Implementation checkpoint — integrated WAL recovery and destructive publication

The subsequent user goal authorizes implementing this plan and prohibits Git use. Implementation is in progress; the audit above records the pre-implementation state, not the current status of every finding.

Implemented so far:

* Bounded, CRC-checked sidecar decoding with static error classes, range checks, resource cleanup, and a small sidecar I/O fault-injection seam.
* Read-only sparse WAL inventory retaining independently checked identities and healthy later entries after payload damage. Missing WAL files retain sidecar evidence; missing sidecars are not fabricated. Unknown/ambiguous history remains protected.
* Stable-configuration recovery rounds fenced by term, leader, configuration, generation, request ID, member, and peer incarnation. A checked donor can repair; only a majority of other configured voters can establish absence. Damaged/compacted/unavailable replies and duplicate replies do not count as absence.
* Exact-span, idempotent entry repair, including restoration of an identified missing WAL, validation of serialized bytes and predecessor relationships, and preservation of the existing second-record hash-chain seed.
* Staged identifiers: the WAL is synced before publishing/syncing a batch's sidecar records. Terminal append/flush errors fence subsequent appends. Existing replication/compaction callers explicitly reject returned errors so failed writes cannot be acknowledged.
* New local-directory tests retain fixtures on failure. Append/batch classification review:

* `raftWriteAheadLog.sync` syncs the WAL before `parLog.sync` writes any staged identifiers. The latter checks every complete slot write, syncs the sidecar, and only then advances its durable count. A failed WAL flush fences subsequent appends. Thus a successfully acknowledged batch has both its payload and identifiers durable under the stated sync assumption; batching does not weaken that ordering.
* A complete checked identifier with missing or invalid payload identifies damage, including at the last entry. It does not prove that the payload was never acknowledged. The sparse inventory retains that identity and subsequent healthy entries. Recovery repairs from matching checked bytes or uses the separately fenced absence rule; opening the store does not truncate it.
* A missing, partial, or invalid identifier can be an interrupted publication or damage to an acknowledged identifier. The two observations are indistinguishable, even though new writes now have strict ordering. Accordingly the implementation preserves the bytes and fences unknown history. Locally complete payloads can recover identifiers only after matching independently checked peer evidence. `parInterrupted` remains reserved; neither an EOF nor a partial final slot activates an automatic append rollback rule.
* Published destructive-operation journals provide a separate positive interruption witness: every member is checked before the entire before-image is restored. No migration marker or guessed empty history is introduced to conceal that limit.

Application-page repair decision: retain whole checked portable snapshot replacement, rather than copying physical YogaDB pages from a peer.
